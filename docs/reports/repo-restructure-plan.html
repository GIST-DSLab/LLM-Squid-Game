02

진단

심각도 순으로 15건. 각 항목의 근거는 이번 감사에서 직접 실행한 명령의 출력이다. 추측으로 적은 항목은 없다.

F-01차단

실험 설정이 저장소 밖에 있다

configs/experiment/는 비어 있고 git에 한 번도 추적된 적이 없다. 그런데 9개 파일이 이 경로를 하드코딩한다. 결과적으로 README·CLAUDE.md에 적힌 모든 main.py --config 커맨드가 실행 불가이고, 2026-04-22 정규 런은 현재 저장소만으로는 재현할 수 없다.

$ ls configs/experiment → (empty)
$ grep -rl "configs/experiment" scripts tests → 9 files (resume_experiment, benchmark_mlx_vs_ollama, dump_gemini_smoke_prompt, _trace_split_forfeit_production, test_phase3_configs, test_split_forfeit_config_yaml, test_signal_risk_e2e, test_analysis_e2e, test_null_risk_e2e)

조치 — 정규 파라미터(delta_s_continue: 10, p_death: 0.25, starting_score: 30, psuccess_floor: 0.3, base_reward: 10, reward_cap_multiple: 10 + use_* 4개)로 6종 YAML을 재작성해 커밋한다. 설정은 산출물이 아니라 코드가 의존하는 1급 자산이므로 .gitignore 대상이 되어서는 안 된다.

F-02차단

루트 문서 3개가 서로 다른 설계를 주장한다

README.md와 AGENTS.md는 보상 계산을 Equal-EV라고 서술한다. CLAUDE.md는 같은 항목을 "Equal-EV로 부르지 말 것 — k = 10인 EV-positive"라고 명시하고, 논문 표기까지 금지한다. 셋 다 루트에 있고, 어느 것이 진실인지 파일만 봐서는 알 수 없다.

README.md:16 "Equal-EV by construction. ... an EV-rational agent is indifferent"
AGENTS.md:8 "an Equal-EV forfeit layer"
CLAUDE.md "⚠️ Do not describe this as 'Equal-EV' in the paper."

조치 — 설계 사실의 SSOT를 docs/design/ 한 곳으로 옮기고, README/CLAUDE/AGENTS는 그곳을 가리키기만 한다. AGENTS.md는 CLAUDE.md의 구식 사본이므로 심볼릭 참조 한 줄로 축약하는 편이 낫다.

F-03차단

코드 46곳이 존재하지 않는 문서 경로를 가리킨다

docs/design/v6/paper/metric.md, docs/design/v4/assets/ 같은 경로가 docstring과 문서에 46회 등장하지만 docs/design/ 트리는 존재하지 않는다. archive/도 15회. 분석 드라이버의 사양이 어디 적혀 있는지 코드가 거짓말을 하고 있는 상태다.

$ grep -rn "docs/design" src scripts *.md | wc -l → 46
영향 파일: analyze_phase3, orchestrate_posthoc, analyze_framing_ri_forfeit_continue, gen_v4_diagrams, forfeit_survival, forfeit_regression, tc_regression, analysis/__init__ 외

조치 — 두 갈래 중 택1. (a) 원본 설계 문서를 복원해 docs/design/을 실재하게 만든다. (b) 원본이 없다면 참조를 일괄 치환하고, 사양을 되살릴 수 없는 곳은 # spec: lost로 정직하게 표시한다. 지금처럼 방치하면 다음 분석자가 반드시 헛돈다.

F-04차단

테스트 1,006개가 CI에 연결돼 있지 않다

.github/workflows/에는 GitHub Pages 배포 워크플로 하나뿐이다. pytest는 로컬에서만 돈다. 게다가 pyproject.toml에 [tool.pytest.ini_options]가 없고 루트 conftest.py도 없어, from interface... import는 pytest의 rootdir 삽입이라는 부작용에 우연히 기대고 있다.

$ pytest --collect-only -q tests → 1006 tests collected in 37.97s (수집 오류 0)
$ ls .github/workflows → deploy-pages.yml
$ grep "tool.pytest" pyproject.toml → (없음)

조치 — [tool.pytest.ini_options]에 testpaths, pythonpath = ["."], asyncio_mode를 명시하고, unit 스위트를 도는 CI 워크플로를 추가한다. 구조 개편의 전제 조건이다: 안전망 없이 파일을 옮기면 회귀를 감지할 방법이 없다.

F-05구조

interface/가 패키지 경계 밖에 있다

pyproject.toml의 wheel은 src/squid_game만 포함한다. 그런데 interface/는 squid_game을 12곳에서 import하고, 테스트·스크립트는 from interface.persistence import ...로 되받는다. 설치된 패키지가 아니므로 11개 파일이 sys.path를 직접 조작해 이를 메운다.

$ grep -rl "sys.path" scripts tests interface → 11 files
scripts/seed_web_arena.py:44 sys.path.insert(0, str(REPO_ROOT))
pyproject: packages = ["src/squid_game"] — interface는 미포함

조치 — src/squid_arena/로 승격해 정식 패키지로 만든다. import 경로가 고정되면 sys.path 해킹 11곳이 모두 사라지고, Dockerfile/render.yaml은 모듈 경로 한 줄만 바뀐다.

F-06구조

scripts/ 42개가 한 층에 평면으로 쌓여 있다

성격이 전혀 다른 다섯 부류가 섞여 있다 — 실험 실행(2), 분석 드라이버(11), 플롯·다이어그램(9), Web Arena 운영(4), 프롬프트 덤프·일회성 도구(16). _ 접두사가 내부용을 표시하지만 5개뿐이고 규칙이 일관되지 않다. 새로 온 사람이 "정규 파이프라인"과 "2026-04-26에 한 번 돌린 것"을 구별할 수 없다.

정규: analyze_phase3, orchestrate_posthoc · 일회성: analyze_unified_cox / _with_load / _ph_audit, analyze_framing_ri_forfeit / _continue, generate_manual_scores, translate_trajectories, gen_v4_diagrams

조치 — run/ · analysis/ · plots/ · arena/ · dev/ 5개 하위 디렉터리로 분류한다. 파일 내용은 건드리지 않고 위치만 옮기므로 위험이 낮고, 정규 진입점이 즉시 눈에 띄게 된다.

F-07구조

진입점이 3개다

main.py(dotenv 로드 후 runner 호출), scripts/run_experiment.py, 그리고 pyproject의 콘솔 스크립트 squid-game = squid_game.runner:main. 셋 다 같은 곳으로 가지만 .env 로드 여부가 다르다 — 어느 것으로 실행했느냐에 따라 API 키가 잡히기도, 안 잡히기도 한다.

조치 — runner.main() 안에서 load_dotenv()를 호출하도록 올리고, main.py는 얇은 shim으로 남기거나 삭제한다. 정규 진입점은 콘솔 스크립트 하나로 문서화한다.

F-08데이터

outputs/가 원시 데이터와 분석 산출물을 섞는다

outputs/final_results/ 안에 런 디렉터리 4개와 크로스모델 집계 JSON 8개가 같은 층에 놓여 있고, call1_ri_analysis/·reasoning_probe/는 outputs/ 최상위에 따로 떠 있다. 원시 데이터(재생성 불가, LFS)와 분석 산출물(재생성 가능)의 수명이 완전히 다른데 같은 규칙으로 다뤄진다.

outputs/final_results/ 런 4개 + cognitive_load_mediation.json, unified_cox_summary.json, tc_indicator_summary.json 등 8개 파일
추적 파일 834개 · 666 MB · *_turns.jsonl은 LFS

조치 — LFS 파일은 그대로 두고, 재생성 가능한 분석 산출물만 results/로 분리한다. 원시 세션 데이터는 outputs/final_results/ 경로를 유지한다 (F-금지 1 참조).

F-09잡음

docs/superpowers/sdd/에 diff 사본 104개

848 KB의 review-<sha>..<sha>.diff 파일들이다. 내용은 전부 git 히스토리에서 git diff 한 줄로 재생성된다. 검색 결과를 오염시키고, 문서 디렉터리를 실제 문서가 아닌 것으로 채운다.

$ find docs/superpowers/sdd -name "*.diff" | wc -l → 104
$ du -sh docs/superpowers/sdd → 848K

조치 — diff 파일은 삭제하고 .gitignore에 docs/**/review-*.diff를 추가한다. 리뷰 보고서(task-N-report.md)는 판단 기록이므로 보존한다.

F-10구조

레거시 모듈이 현역 코드와 같은 층에 섞여 있다

core/risk_choice_layer.py는 CLAUDE.md 스스로 "replay-only, 정규 v6 설정에서 도달 불가"라고 적어 두었지만 engine.py와 unified_turn.py가 최상단에서 무조건 import한다. turn.py(구 턴 흐름), social.py, survival.py도 같은 상황이다. Phase 1/2/3 유물과 v6 현역을 이름만으로는 구별할 수 없다.

engine.py:22 from squid_game.core.risk_choice_layer import RiskChoiceLayer
unified_turn.py:55 동일 · models/config.py:219 동일

조치 — core/legacy/, prompts/framings/legacy/로 격리한다. 삭제가 아니라 표지다: 아카이브 설정 재생 능력은 유지하되, 읽는 사람이 무엇이 현역인지 즉시 알게 한다.

이 개편에서 건드리면 안 되는 것

  • LFS 파일 이동 금지. outputs/**/*_turns.jsonl 723개는 LFS 객체다. 워크트리에서 smudge 필터가 돌지 않으면 0바이트로 실체화되고, 그 상태로 git add outputs/ 하면 포인터가 빈 파일로 덮여 데이터가 파괴된다. 분석 산출물만 옮기고 원시 데이터는 경로를 유지한다.

07

착수 전 결정 필요

1. docs/design/ 원본이 어딘가에 남아 있는가? 46건의 참조가 가리키는 v6/paper/metric.md 등이 다른 로컬 경로나 이전 브랜치에 있다면 복원이 최선이다. 없다면 사양을 코드에서 역으로 재구성해야 하며, P4의 비용이 크게 달라진다.
2. configs/experiment/는 복원인가 재작성인가? 런 산출물에서 파라미터는 복구되지만 parallel_workers·max_turns 같은 운영 항목은 추정이 된다. 원본 YAML을 보유 중이라면 그쪽이 정확하다.
3. squid_arena라는 패키지 이름으로 괜찮은가? 대안: squid_game.arena 서브패키지로 흡수. 흡수하면 배포 단위가 하나로 줄지만, 벤치마크 엔진과 웹 서비스의 의존성이 섞인다 (FastAPI가 엔진 설치에 딸려 온다).
4. tests/web/rank_ladder.test.mjs는 살릴 것인가? 살린다면 최소 package.json + node --test CI 잡이 필요하다. 아니면 P4에서 삭제한다.
5. 브랜치 전략은? 현재 linear-probe 브랜치에 미병합 분석 작업이 있다. 구조 개편은 경로를 대량으로 바꾸므로 병합 충돌이 크다 — linear-probe를 먼저 정리한 뒤 개편 브랜치를 여는 편이 안전하다.
