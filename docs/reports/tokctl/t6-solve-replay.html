SOLVE 재생: DeepSeek은 상한을 보지 않는다

← 하네스 프롬프트 흐름 §6 · t1 기록 진단 · t2 하네스 캡처 · t3 같은 입력 재생 · t4 한 가지씩 바꾸기 · t5 게임으로 확인 · t6 SOLVE 재생 · t7 보정과 상한 맞춤 · t8 v34 본 런 · t9 승패 요인 · v35

TALK를 고친 뒤(t5) DeepSeek은 대화로는 꺼지지 않았지만 SOLVE에서 모두 꺼졌습니다. 기록된 SOLVE 장면 16개(v33 Claude·GPT-6 판, 정답 포함)를 그대로 다시 보내 채점했습니다. 답 상한은 원래 장면의 상한(그 solver의 잔액, 중앙 25,926)이고, 상한에 닿은 답은 엔진처럼 무효입니다.

  • 원래 답(Claude·GPT-6): 16개 중 13개 정답, 중앙 930토큰.
  • DeepSeek은 추론은 맞지만 15~30배 길게 합니다. 상한을 무시하면 10~13/16 정답인데, Codex high·medium·low와 Claude Code high·low 모두 중앙 16k~29k토큰을 써서 4~9개가 상한을 넘습니다. SOLVE 화면 첫 줄이 "Your limit: at most N tokens … including your thinking"인데도 길이를 맞추지 않습니다. 하네스를 바꿔도(Claude Code) 같습니다.
  • 생각 예산은 Ollama에서 걸리지 않습니다. Anthropic 경로의 budget_tokens(2,000·6,000)를 Ollama가 무시해 상한까지 생성했고(6번 중 4번 무효), 네이티브 API로 예산만큼 생각시킨 뒤 답 형식(BELIEF:)을 미리 채워 이어 쓰게 해도 5번 중 3번은 답 글에서 추론을 다시 시작했습니다(budget_tries.json).
  • DeepSeek none: 생각 없이 중앙 28토큰, 상한 넘김 0, 9/16 정답 — GLM high(9/16)와 같은 수준입니다.
  • Gemma는 high에서 중앙 7.8k로 길지만 넘김 0, 13/16. GLM은 high에서 중앙 690토큰, 넘김 1, 9/16.
  • 보정 규칙: SOLVE 수준 = 이 16장면에서 상한을 넘기지 않는 가장 높은 수준. GLM·Gemma는 high, DeepSeek은 none이 됩니다(TALK 수준은 t4의 24장면에서 가장 싼 정상 형식). 새 모델도 같은 두 재생으로 정합니다.

결론: DeepSeek의 SOLVE 실패는 하네스가 아니라 모델이 상한을 보고 추론 길이를 맞추지 못하는 데서 옵니다. 하네스로 걸 수 있는 장치(effort · budget_tokens · 예산 후 강제 답) 가운데 상한을 지키는 것은 none뿐이고, 그때 정답률은 GLM과 같은 9/16입니다. 이 설정으로 DeepSeek을 다시 게임에 넣었습니다(t7).
