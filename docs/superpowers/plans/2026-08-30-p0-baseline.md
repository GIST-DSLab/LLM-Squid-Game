## Harness defect found and fixed during capture

The task brief's reference implementation of `build_manifest` namespaced
multi-root keys by `root.name`. In production every root passed to it is a
run's `phase3_analysis` directory (`run / "phase3_analysis"`), so
`root.name` is literally `"phase3_analysis"` for all four canonical runs --
every run's keys collided in the manifest dict, and only the
alphabetically-last run's 21 entries survived. The first capture attempt
copied all 84 files onto disk correctly but recorded only 21 keys in
`manifest.json`, silently leaving three of the four runs ungated. Fixed by
keying on `root.parent.name` (the run directory's own name) instead of
`root.name`; re-captured afterward with the corrected code, yielding the 84
entries recorded above. See `scripts/dev/golden_snapshot.py`'s
`build_manifest` docstring for the in-code explanation.

# Operating the safety net (added 2026-08-30, final review fix wave)

Everything below was previously held only in `.superpowers/`, which
`.gitignore` excludes. It is recorded here so that anyone running P1 from a
fresh clone or a new session has it.

## Model label: read it from the run, never from the directory name

`golden_snapshot.run_analysis` passes `--model` to `scripts/analyze_phase3.py`.
That label is written into **seven** artefacts per run (`long_format.csv`,
`manipulation_check.md`, `regime_stratified_results.md`,
`season_summary.csv`, `unit13_results.md`, `unit14_results.md`,
`unit15_results.md`).

Nine files per run were dirty before the fix, but only these seven for the
label reason. The other two -- `unit14_turn_observations.csv` and
`regime_stratified_turn_observations.csv` -- have no model column at all;
they were dirty for the unrelated `reward_received` reason documented in the
next section, and they stay dirty after the fix.

The first implementation passed `run.name` -- the run DIRECTORY name
(`20260422_0218_gemini-2.5-flash_signal-game`) -- where the committed
artefacts carry the model label (`gemini-2.5-flash`). That made the golden
snapshot a mislabelled copy of the paper's results and left 36 tracked files
dirty after every `verify`.

`golden_snapshot.model_label(run)` now reads
`seasons[0].provider_config.model` from the run's own
`experiment_config.json` and applies the same path-safe slug the runner uses
when naming an output directory (`:` and `/` -> `-`). The slug is required:
three of the four canonical runs record `gpt-oss:20b-cloud`,
`nemotron-3-nano:30b-cloud`, `qwen3-next:80b-cloud`, while every committed
artefact spells them with hyphens. If the key is absent the function raises
`SystemExit` naming the run -- there is deliberately no fallback to
`run.name`, since that fallback is the defect.

  - `20260422_0902_qwen3-next-80b-cloud_signal-game/unit14_turn_observations.csv`

  Cause: commit `f745eef` (2026-07-04, *"feat(analysis): turn_observations
  emits reward_received column"*) added a `reward_received` column to the
  turn-observation frame. The artefacts committed under `outputs/` were
  produced by the 2026-04-22 runs and committed in the initial commit; they
  have never been regenerated since, so they lack that column. Every value
  they do carry is unchanged -- the whole-file diff is the one added column
  shifting each row. Regenerating them would mean `git add outputs/`, which
  is forbidden, so they stay stale and the drift is documented here instead.

**Compensating step, mandatory after any `verify` or `capture`:**

```
git checkout -- outputs/final_results
```

`git add outputs/` is **never** allowed. Those `*_turns.jsonl` files are Git
LFS objects (666 MB of irreplaceable raw session data); staging them from a
worktree that skipped the LFS smudge overwrites the pointers with empty
files. `git checkout -- outputs/final_results` is the only sanctioned way to
put the tree back.

After that restore, `git status --porcelain -- outputs/` is empty, and
`verify --skip-analysis` reports the 8 files above as `changed` -- expected,
for the reason given. The gate is golden-vs-regenerated, not
golden-vs-committed.

## Importing a module can write into `outputs/`, and `git status` cannot see it

`tests/unit/test_import_smoke.py` imports every module in `src/`, `scripts/`
and `interface/`. Five modules do filesystem work at module scope, so the
import itself is not free:

| module | what it does at import | handling |
|---|---|---|
| `scripts/build_llm_experience_diagram.py` | writes a `.excalidraw` into `docs/design/v4/assets/` | skipped, named |
| `scripts/build_posthoc_analysis_diagram.py` | same | skipped, named |
| `scripts/build_prompt_flow_diagram.py` | same | skipped, named |
| `interface/anthropic_proxy.py:57` | `mkdir -p outputs/api_sessions/thinking_traces` | sandboxed via `SQUID_THINKING_LOG_DIR` |
| `interface/api.py:144` | `get_repository()` -> `mkdir` + `sqlite3.connect` + `init_schema()` on `outputs/web_arena/web_arena.db` | sandboxed via `WEB_ARENA_DSN=":memory:"` |

**Neither of the last two is visible to `git status`.** `outputs/api_sessions/`
is an untracked *empty* directory and git does not track those;
`outputs/web_arena/` is gitignored (`.gitignore:32`). A clean `git status`
is therefore *not* evidence that a test left `outputs/` alone. Check with
`ls outputs/` plus `stat` on `outputs/web_arena/web_arena.db` instead.

The `interface.api` hazard is **order-dependent**: in a full
`pytest tests/unit` run, `test_api_web_arena.py` imports the module first
inside a fixture that already sets `WEB_ARENA_DSN=":memory:"`, so the smoke
test gets a harmless cache hit. Running
`pytest tests/unit/test_import_smoke.py` **alone** is the case that opens the
live 141 MB dev DB. Reproduce hazards of this shape by running the single
file, never only the whole suite.

`test_importing_writes_nothing_into_outputs` asserts the sandbox actually
holds, so a future change that hardcodes either path fails loudly instead of
silently re-opening the write path. Re-run the module-scope audit (the `grep`
in that file's docstring) after any restructure step that moves code between
modules.

## `motivation.py`: a reordering will legitimately move the bootstrap CIs

`motivation.compute_motivation_decomposition` seeds a single
`np.random.default_rng(seed)` and threads that one generator through the
**four** estimators that bootstrap, in a fixed call order: `_survival_drive`,
`_task_curiosity`, then the baseline-persistence pair
(`_baseline_persistence_cognitive`, `_baseline_persistence_behavioral`).
Each consumes draws from the shared stream, so **reordering them changes
every subsequent estimator's bootstrap CI** even when the statistics are
otherwise untouched.

`_score_attachment` sits between them in the call order (`motivation.py:452`)
but takes no `rng` parameter and consumes nothing, so moving it alone has no
effect on the stream.

If P2 reorders them and `motivation.json` mismatches, read that as
reordering, **not** as a numerical regression. Confirm by restoring the
original call order and re-verifying before concluding anything else.

## `configs/experiment/phase3_split_forfeit_smoke.yaml` writes into `outputs/`

That config has `output_dir: outputs` (line 274, verbatim from the source
run). An actual smoke run therefore drops a new untracked run directory under
`outputs/` and makes `git status --porcelain -- outputs/` non-empty for
reasons unrelated to the analysis artefacts.

There is **no clean-tree guard in code** -- neither `golden_snapshot.py` nor
any test checks that `outputs/` is clean. "`git status --porcelain --
outputs/` must be empty" is a manual convention this document asks you to
follow, and a smoke run breaks it by hand, not by tripping an assertion.
Point `--output-dir` elsewhere, or delete the created directory afterwards --
and never delete anything that was already there.
