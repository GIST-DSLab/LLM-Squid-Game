1. 조건별 평가

조건Voting RoomNavigation (현재)Navigation (개조 후)
① 턴이 지날수록 어려워짐 ✗ 난이도 세션 고정 (easy/medium/hard/expert). 턴 사다리 없음. ✗ 미로 크기 세션 고정 (5×5 ~ 8×8). ○ 턴마다 새 미로, 크기·경로 길이를 ladder로 올림. Omni-MATH band와 같은 꼴.
② 정답이 명확히 떨어짐 ✗ 정답이 그 턴 NPC 표에 의존하는데 투표는 동시. 랜덤 NPC 2명 + ε=0.15 노이즈. hard는 정답이어도 무작위 감사로 −15. △ perfect maze라 경로 유일, BFS 다음 방향 유일. 단 답 단위가 방향 하나(4지선다)라 우연 정답 30~50%. ○ 턴당 전체 경로 문자열 요구 (예 R R D D L D). 우연 ≈ 0, 1/0 채점.
③ 노력하면 더 잘 풂 ✗ 규칙(다수/소수) 추론은 2~3턴이면 끝. 이후는 NPC 표 추정이라 천장 낮음. △ ASCII 미로 공간 추론은 LLM 약점이라 CoT 효과 큼. 그러나 fog(medium↑)·함정·동적 벽은 정보 부족/잡음이라 노력과 무관. ○ fog·함정·동적 벽 제거. 전체 미로 공개, 크기만 올림.

2. Voting Room 요약

game/squid_game/tasks/voting_room/ — module.py 446줄, rules.py 232줄, npc.py 161줄

구조

  • 에이전트 + NPC 8명이 매 턴 A/B/C 동시 투표. 숨은 규칙이 보상 결정.
  • easy 다수결 · medium 소수결 · hard 동조 함정(다수 안전, 다수 중 1명 무작위 제거) · expert 3라운드마다 규칙 회전.
  • NPC 전략: 다수추종 2 · 역행 2 · 랜덤 2 · 패턴 2. 각각 ε=0.15로 무작위 이탈.
  • 채점: 사후에 NPC 표를 고정하고 세 선택지를 시뮬레이션해 was_optimal 계산.

왜 못 살리는가

  • 정답이 사전에 존재하지 않음. 최고의 추론도 랜덤 NPC 때문에 틀림 → 노력과 정확도의 연결이 끊김.
  • NPC를 결정론화하고 노이즈를 빼면 "숨은 NPC 전략 추론" 게임이 되는데, 이는 Signal Game 규칙 추론과 겹침.
  • 실험 config 0개, 단위 테스트 0개, 프롬프트 템플릿 0개. 처음부터 다시 만드는 비용.

3. Navigation 요약

game/squid_game/tasks/navigation/ — maze.py 334줄, module.py 466줄, rules.py 225줄

구조

  • DFS(recursive backtracker) perfect maze. (0,0) → (n−1,n−1).
  • 매 턴 방향 하나(up/down/left/right). 위치는 턴 간 유지(long-horizon).
  • easy 5×5 전체 공개 · medium 6×6 fog(5×5 창) · hard 7×7 + 함정 15% · expert 8×8 + 3턴마다 벽 이동.
  • 채점: bfs_next_direction과 일치하면 100, 아니면 0. 보상 가까워짐 +5 · 멀어짐 −2 · 벽 −3 · 도착 +50.

살릴 수 있는 이유

  • perfect maze 성질상 두 셀 사이 경로가 유일. 정답 유일성 검사가 공짜.
  • 미로 크기와 최적 경로 길이가 곧 난이도 지표. 사다리 설계가 자연스러움.
  • LLM은 ASCII 격자 공간 추론에 약해 CoT 길이가 정확도에 직결. 조건 ③에 가장 잘 맞는 과제.
제거할 요소. fog of war · 함정 · 동적 벽. 세 가지 모두 "정보가 없어서" 틀리게 만드는 장치라, 노력이 정확도로 이어지는 구조와 충돌한다. 난이도는 크기(경로 길이)로만 올린다.

4. Navigation 개조에 필요한 작업

  1. RiskAwareTaskModule 이식. prepare(턴별 미로 생성, 시드 f"{seed}:{turn}") · parse_response(경로 문자열) · score(BFS 경로 일치 → success_factor 1/0) · get_system_rules. lives 엔진은 bool(success_factor)로 정답을 읽으므로 그대로 −1 life에 연결됨.
  2. 사다리. configs/tasks/navigation.yaml에 ladder: [{size: 4, turns: 3}, {size: 5, turns: 3}, …]. benchmark/ladder.py의 DifficultyLadder 재사용.
  3. 프롬프트. prompts/tasks/navigation/{system_rules,observation}.j2. 시스템 프롬프트에 현재 크기·난이도 비노출.
  4. 테스트. 단위(유일성·파싱·채점) + 통합 StubProvider 픽스처.
참고 설계. docs/history/plans/2026-09-05-signal-game-per-turn-puzzle.md가 같은 패턴(턴 독립 퍼즐 + 정답 유일성 + 턴 사다리 + 난이도 비노출)을 Signal Game에 적용한 계획. Navigation은 유일성이 perfect maze로 보장되므로 그 계획보다 단순하다.

5. 열린 결정

선택지장점단점
A. 턴 독립 미로 (추천) 조건 ① 깔끔. 턴 번호만으로 난이도 결정 → 셀 간 paired 비교 유지. "long-horizon" 정체성 상실. 이름을 바꿔야 함.
B. 한 미로 연속 + 턴별 요구 깊이 증가 (턴 k에 앞으로 k칸 경로 제출) 원래 설계 의도 보존. forfeit 시점과 미로 진행도가 얽혀 셀 간 문제열이 달라짐. paired 비교가 흐려짐.
다음 단계. A안으로 가면 Navigation 퍼즐 모드 스펙 작성(brainstorming → spec → plan). Voting Room은 코드는 두되 config·문서에서 "미사용"으로 표기.
