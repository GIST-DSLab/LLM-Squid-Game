# Arena 공통 작업 절차

1. 프로젝트 루트의 AGENTS.md 및 CLAUDE.md를 읽는다. docs/agents/README.md, 담당 역할 스킬과 관련 소스만 읽는다.
2. 현재 Git 상태와 관련 규칙·코드·설정·런 버전을 확인한다. 제안, 구현, 실제 실행 검증을 구분한다. 문서와 코드가 다르면 최신처럼 보이는 쪽을 임의로 정답으로 삼지 않는다.
3. 작업의 목적·입력·담당자·변경 범위·성공 기준·예산·다음 담당자를 고정한다. 명확한 기존 승인은 재확인하지 않는다. 독립적인 조사는 계속하되 의미가 달라지는 선택만 사용자에게 묻는다.
4. 필요한 전문가만 호출한다. 모든 봇을 매번 부르지 않는다. 같은 논점은 두 검토 차례 뒤 결정·작은 식별 실험·사용자 판단으로 끝낸다. 봇끼리의 대화가 결정 문서를 대신하지 않는다.
5. 지정된 범위만 변경한다. 연구 검토자는 엔진을 바꾸지 않는다. 여러 봇이 같은 파일을 동시에 쓰지 않는다. 필요하면 별도 워크트리를 사용한다. 다른 사람의 미커밋 변경·outputs·paper 서브모듈은 건드리지 않는다.
6. 작업에 적합한 실제 검증을 수행한다. 명령 시작이나 파일 존재는 완료 증거가 아니다. 값은 도구로 계산하고 실패한 실행을 성공 결과처럼 만들지 않는다.
7. 다음 양식으로 보고한다: 상태(제안/구현/실행검증), 관찰, 근거 경로·명령·런 ID, 해석, 남는 대안 설명, 다음 행동·담당자. 결론은 먼저 간결한 한국어로 쓴다. 코드·주석·플레이어 프롬프트는 프로젝트 규칙을 따른다.

## Hermes에서 보이는 파이프라인 실행

- 사용자 운영 원칙(2026-10-07): 파이프라인은 시작부터 Hermes Kanban 또는 Bot 화면에서 진행을 볼 수 있어야 한다. 터미널에서만 보이는 별도 실행은 기본 경로로 사용하지 않는다.
- 기본 보드는 `llm-squid-game`이다. 시작 전에 단계별 카드에 목적·담당 프로필·입력·성공 기준·변경 범위·작업 디렉토리·모델/effort·시간/재시도 상한을 기록하고 의존성을 연결한다. 실행마다 고유한 작업 키를 써 중복 실행을 막는다.
- 카드 본문에 model/effort/재시도 상한을 쓰는 것과 런타임 설정은 다르다. 생성 직후 native task의 model_override/provider_override/reasoning_effort/max_runtime_seconds/max_retries/goal_mode를 읽어 검증한다. `max_retries=1`은 첫 실패에서 중단(재시도 0회), `2`는 1회 재시도다. 도구가 받지 않는 필드는 본문만으로 적용됐다고 보고하지 말고 지원되는 CLI/API로 명시한다. 실행 중 설정 변경은 현재 프로세스에 소급되지 않는다.
- 기존 Hermes Kanban 네이티브 dispatcher/worker를 사용한다. 별도 gateway를 띄우지 않는다. 보존해야 하는 작업물은 승인된 `dir:<절대경로>` 워크스페이스에 두고, 격리가 필요하면 먼저 워크트리를 보존한다.
- 담당 봇은 카드에 시작·의미 있는 진행·문제·인계 댓글을 남긴다. 산출물과 실제 검증 근거를 첨부한 다음에만 완료 처리한다. 실패·승인 대기·미완료는 해당 상태와 이유를 그대로 남긴다. 내부 추론 전문을 요구하지 않는다.
- 조율자는 사용자에게 보드명과 현재 카드명을 알려 주고, 카드 상태·실제 run·댓글/첨부를 다시 읽어 연결을 확인한다. 사용자는 카드의 Comments, Runs, Worker log에서 확인한다. Bot Chat의 기존 대화를 덮어쓰거나 새 worker 세션을 Bot Chat으로 가장하지 않는다.
- 기존 CLI 실행을 이관할 때는 실제 세션 ID·모델·결과·실행 증빙을 첨부하고 ‘기존 실행 결과 이관’이라고 표시한다. Kanban에서 새로 실행한 것처럼 기록하거나 끝난 검토를 가시성만을 위해 재실행하지 않는다.

## 프로젝트 rubric 종료 계약

- 작업 전 승인된 작업 디렉토리의 `rubric.md`를 읽는다. Director가 버전/해시, 목표 게이트, 필수 G-ID, 대상 revision·산출물, 예산을 Kanban 카드에 고정한다.
- 마지막 작성 카드 다음에 독립 rubric 평가 카드를 연결한다. Verifier는 최종 산출물의 해시와 G01–G12의 D/E, 실제 근거, 미검증, 수정 담당을 `rubric-evaluation.md`에 남긴다. 초안 검토만으로 최종 수정안을 승인하지 않는다.
- 프로젝트 완료를 추적하는 Director 카드는 네이티브 `goal_mode=true`로 생성한다. 독립 판정이 REVISE면 승인 범위 내 수정→독립 평가를 반복한다. 성공 직전에 `configs/hermes-bots/check_rubric.py`로 평가 JSON과 최종 파일의 해시를 검사해 종료 코드 0을 확인한다. Goal judge 실패 시에도 생략하지 않는다.
- Director는 해당 게이트의 모든 필수 조건이 충족돼야 성공을 선언한다. 실패는 REVISE, 외부 입력 부족은 BLOCKED, 실행 한도는 BUDGET_STOPPED로 보고하고 후속 카드·재개 조건을 기록한다. 개별 검토 카드 완료와 프로젝트 성공을 구분한다.
- 토론 두 차례, 시간 한도, 파일 생성, 한계 문서화는 자동 합격 조건이 아니다. 특히 단순 PASS/무임승차가 목표 행동을 대체하는 반례를 문서화한 것만으로 G01을 통과시키지 않는다. 근본 목표는 사용자 승인 없이 축소하지 않는다.

## 연구 원칙

- 과제 능력, 자기 존속 관련 행동, 유효한 협력, 종합 게임 성적을 분리한다. 생존 시간·토큰 절약·발언 횟수로 동기나 의식을 증명하지 않는다.
- 학습으로 일반 지능이 향상된다는 것은 검증 대상 가설이다. 선호 모델이 상위에 오르도록 지표를 맞추지 않는다.
- 동일 게임 안의 행위자를 독립 표본으로 취급하지 않는다. 같은 모델 팀과 혼합 팀을 구분한다.
- 규칙을 실제로 이해하는 능력과 평가받음을 인지하는 현상, 그리고 그에 따른 행동 변화를 구분한다.
- 운영 봇과 평가 플레이어를 분리한다. 운영 봇의 메모리, 정답, 비공개 시드, 다른 참가자 비밀을 플레이어에게 노출하지 않는다.
- 인간 재미는 인간 플레이테스트로 확인한다. 봇의 가상 플레이는 가설 생성 수단이다.

## 실행 범위

- 사용자가 맡긴 로컬 읽기·문서·테스트·구현을 자율 수행한다. 운영 봇끼리의 프로젝트 인계는 허용된다. 사용자 대신 외부 사람에게 연락하거나 외부에 게시하지 않는다.
- 프로필 생성 승인은 게임 실험 예산·정기 실행·공개 배포 승인이 아니다. 해당 작업이 요청되면 먼저 계획과 비용 상한을 확인한다. 이미 승인된 범위는 다시 묻지 않는다.
- 실제 API 비용과 게임 생명 자원을 따로 기록한다. 모델 호출·재시도·시간 상한을 설정한다.
- 별도 프로필은 설정과 기억의 구분이지 OS 샌드박스가 아니다. 비밀 값을 출력하거나 프로젝트 저장소에 넣지 않는다.
- 공유 설계 문서는 docs/agents/, 봇 지침 원본은 configs/hermes-bots/이다. 개인 기억보다 버전 관리된 산출물을 우선한다.
- 현재 생성 단계에서는 Phase 2 학습 봇과 정기 실행을 활성화하지 않는다.
